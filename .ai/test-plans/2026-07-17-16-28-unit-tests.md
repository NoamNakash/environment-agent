# Unit Test Plan: Environment Agent

## Overview

This plan identifies pure logic functions suitable for isolated unit testing in the DCM Environment Agent. Following strict BDD principles, we test **only** algorithmic behavior with no external dependencies — configuration parsing/validation, data structure operations (slot management, deny list), mathematical formulae (backoff), pattern matching (provider ID, topic name), state machine transitions (health), and structured data assembly (CloudEvents, RFC 9457 errors).

**Excluded from unit tests (covered by integration tests):**
- HTTP handler behavior (request/response lifecycle, middleware ordering)
- NATS/JetStream interaction (topic creation, consumer binding, ack/nack)
- REST client behavior (DCM registration calls, SP health poll calls)
- Persistence layer I/O (file read/write, corruption handling)
- Signal handling and graceful shutdown
- Logging output assertions (framework-mediated)

**Excluded by Caller-Trust Principle:**
- Validating that callers pass non-nil arguments where the type system prevents it
- Re-checking preconditions the router/framework already guarantees (e.g., method matching)

### UT-RTE-045: In-flight lock never evicts and provides idempotent claim/release

- **Validates AC:** AC-RTE-210 (in-flight mutual exclusion; behavioral double-dispatch coverage is

### UT-RTE-047: In-flight lock mutual exclusion survives adversarial claim/release ordering

- **Validates AC:** AC-RTE-210 (in-flight lock)
- **Component Under Test:** in-flight mutual-exclusion lock
- **Given** 50 goroutines continuously racing to claim-then-release the SAME key, 500 iterations

## 5. Retry Backoff Calculation

### UT-DCM-010: Exponential backoff formula without jitter

- **Validates AC:** AC-DCM-050
- **Component Under Test:** backoff calculator (deterministic component)
- **Given** `initialInterval=1s` and `maxInterval=5m`
- **When** calculating backoff for attempt 0
- **Then** the calculated interval (before jitter) MUST be `min(1s × 2^0, 5m) = 1s`
- **When** calculating for attempt 3
- **Then** the calculated interval MUST be `min(1s × 2^3, 5m) = 8s`

#### Boundary Cases
- UT-DCM-011: Attempt 0 → `1s` (no multiplication)
- UT-DCM-012: Attempt 1 → `2s`
- UT-DCM-013: Attempt 9 → `min(512s, 300s) = 300s` (capped at max)
- UT-DCM-014: Attempt 20 → still capped at `300s` (overflow-safe)
- UT-DCM-015: Attempt 1,000,000 against a small (5m) max → still capped at `300s` and terminates immediately (no `O(attempt)` hang) — but on its own doesn't exercise the overflow guard near its actual int64 boundary, since `d` exceeds `max` within a handful of doublings regardless of how large `attempt` is; see UT-DCM-016/017
- UT-DCM-016: Zero `initial` → returns `max` directly, without entering the doubling loop
- UT-DCM-016b: Negative `initial` → returns `max` directly, same as UT-DCM-016 (separate entry since a negative duration is a distinct boundary from zero)
- UT-DCM-017: Attempt 1,000 against `max = math.MaxInt64` → the `d > max/2` overflow guard must fire at exactly the doubling where `d` first exceeds `max/2` (`2^62`, since `max/2 = 2^62-1`), returning `max` without `d` ever overflowing int64. `max = math.MaxInt64` specifically (not merely "large") is required for this test to actually discriminate the guard's presence: with a smaller cap (e.g. `MaxInt64/2`, tried and rejected during review), the next doubling after the guard would still fit in int64, so deleting the guard entirely produces the identical return value — verified directly by running both variants, and by mutation-testing (temporarily deleting the guard in `backoff.go` and confirming this specific test then fails)

  consuming" until process restart — no future reconnect or background retry would ever call
  `beginConsuming` again. See DD-420.
